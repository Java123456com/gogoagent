# 差旅行程方案 → HTML 渲染

## 触发条件

当你（ItineraryPlanAgent）已完成以下步骤：
1. 调用 `plan_itinerary` 生成多套方案
2. 调用 `review_itinerary` 完成审核（含修复轮次）
3. 调用 `finish_subtask` 标记最后子任务完成
4. 调用 `finish_plan` 标记计划完成

此时需要将完整方案展示给用户，使用本 skill 组合 HTML 并调用 `save_plan_html` 工具。

## 方案内容结构与格式要求

### 内容结构模板（倒金字塔，必守顺序）

严格按以下顺序输出方案内容——推荐方案置顶（用户 80% 只看这里就够），审核把关紧随其后、置于明细之前，评估足迹放在最末。以下 Markdown 模板仅作为**内容结构参考**，实际输出为 HTML（CSS 样式参见下方"HTML 组件映射"）：

```markdown
## 🗂️ 差旅行程方案（上海 → 杭州，2026-07-16 去 / 2026-07-18 返）

### 🏆 推荐方案 · 综合最佳

> **🌤️ 天气提醒**：上海 多云，28-35°C；杭州 多云转小雨，26-33°C。出发地天气良好适合飞行，目的地有小雨建议携带雨具，户外活动安排在上午。

### 📋 方案对比（需要挑选时看这里）
| 方案 | 标签 | 去程交通 | 返程交通 | 酒店(房型) | 总耗时 | 总价 | 评分(时/价/偏/体/政/综) | 审核 |
|------|------|----------|----------|-----------|--------|------|---------------------|------|
| 方案1 ✅推荐 | 价格最低/时间最短 | 东航MU5678 07:30→09:45 | 东航MU5679 20:10→22:20 | 全季西湖店/大床房 ¥413晚 | 4h05m | ¥1313 | 80/90/70/85/100/85 | ✅ 通过 |
| 方案2 | 综合最优/最符合偏好 | 国航CA1234 08:00→11:00 | 高铁G7501 19:00→22:05 | 亚朵西溪店/高级房 ¥560晚 | 6h05m | ¥1730 | 90/70/95/40/0/60 | ❌ 未通过 |

### 🔍 方案明细（想核对细节时展开）
- **方案1 · 价格最低/时间最短（✅ 通过）**
  - 去程：东航 MU5678，上海虹桥 07:30 → 杭州萧山 09:45，经济舱 ¥620
  - 返程：东航 MU5679，杭州萧山 20:10 → 上海虹桥 22:20，经济舱 ¥620
  - 酒店：全季酒店（西湖店），大床房，2 晚，¥413/晚，合计 ¥826
  - 总耗时：4h05m ｜ 总价：¥1313 ｜ 评分：时80/价90/偏70/体85/政100/综85
- **方案2 · 综合最优/最符合偏好（❌ 未通过 → 已修复）**
  - 去程：国航 CA1234，上海虹桥 08:00 → 杭州萧山 11:00，公务舱 ¥1200
  - 返程：高铁 G7501，杭州东 19:00 → 上海虹桥 22:05，一等座 ¥210

  - ❌ 未通过原因：总价 ¥1730 超预算 ／ 去程公务舱高于政策舱位标准
  - 🔧 修复：换更经济酒店 + 去程降经济舱 → 生成【方案2-修复版】并通过审核（总价 ¥1450 / 综合 91）

### 👉 下一步
- **确认方案**：告诉我你选哪套方案（如"确认P1"），我再进入预订流程。
- **想调整**：告诉我新的条件（换更近酒店 / 指定航司 / 提高预算等），我按新条件重新规划并审核。

### 🧭 Agent 为你做了什么

- **环境感知**：查询了上海和杭州的天气（上海多云 28-35°C / 杭州小雨 26-33°C）和交通资讯（无异常），因目的地降雨优先推荐高铁出行
- **候选检索**：检索到交通 5 条（去程 3 / 返程 2）、酒店 3 条
- **工具组合**：生成并对比了 6 套可行的「交通 × 酒店 × 返程」组合方案（combo_count）
- **目标筛选**：从 6 套中精选 4 类代表——🥇综合最优=方案2 ｜ 💰价格最低=方案1 ｜ ⏱️时间最短=方案1 ｜ ❤️最符合偏好=方案2（取自 tags）
- **审核剔除**：❌ 未通过 1 套（超预算 / 超政策舱位），经 1 轮重跑修复后全部通过（取自审核 summary）
```

### 数据要求

- **禁止编造方案字段（重要）**：初稿/修复版/最终推荐里的航班号/车次号、承运人、出发/到达时间、舱位/席别、票价、酒店名、房型、晚数、每晚价、总价、总耗时、各维度评分，**必须逐字取自真实数据源**——`plan_itinerary` 的返回（含从 Redis 读取的候选数据）和审核报告；不得自行编造或改写任何数值，数据源中不存在的字段一律留空不写，不得脑补。
- **严禁编造用户偏好（重要）**：只有当 `preferences` 确系来自 `retrieve_from_memory` 且非空、且 planner 返回的 `preference_basis` 明确列出了命中项（如「航司命中:CA」「直飞命中」「可退命中」）时，才可以在文案中描述"方案匹配了您的偏好（某航司/时段/直飞/可退等）"，且只能描述 `preference_basis` 里真实列出的命中项。若 `preferences` 为空字符串 `""`（无长期记忆偏好），或 `preference_basis` 为「无偏好设置，使用中性分」，则**绝对禁止**声称方案匹配了航司、早班机、直飞、可退改、酒店品牌等任何用户未表达的偏好；此时偏好维度一律如实表述为"无个人偏好，按中性分计算"，且不得出现"最符合偏好"标签。

### 格式要求

- **推荐方案（置顶必填）**：先用一句话引用块说明为什么推荐它；紧接一行引用块简述出发地与目的地的天气及交通建议（如「上海 多云 28-35°C；杭州 小雨 26-33°C，建议高铁出行、携带雨具」），无天气数据时省略；随后以表格呈现（列：环节 / 详情 / 费用；行：🛫 去程、🛬 返程、🏨 酒店，末尾加合计行）。去程/返程详情含航班号/车次号、站点、出发/到达时间、舱位/席别，费用列填票价；酒店详情含名称、房型、晚数、每晚价，费用列填酒店合计；合计行的详情列放总耗时（审核报告 `total_transit_hhmm`）与六维评分，费用列放总价（`total_budget`）。
- **审核把关（引用块，显眼但不喧宾夺主）**：用引用块 + ✅/⚠️ 图标，简述推荐方案审核结论 + 全部方案 `summary`（通过/隐患/未通过各几套）+ 修复情况；控制在 2–3 行，不得盖过推荐方案。
- **方案对比表**：每行含标签、去程/返程交通（航班号/车次号 + 出发→到达时间）、酒店(房型)、总耗时（`total_transit_hhmm`）、总价（`total_budget`）、六维评分、审核评级；推荐方案所在行标注 ✅推荐。
- **方案明细**：每套给出去程/返程交通详情（航班号/车次号、出发地→目的地、出发/到达时间、舱位/席别、票价）、酒店（名称、房型、晚数、每晚价与合计）、总耗时与总价、六维评分；未通过/有隐患的方案在其条目内直接列出具体原因（issues）、修改建议（suggestions）与修复结果。
- **评估足迹（最末必填）**：量化本次工作量——① 出发地与目的地天气和资讯查询结果摘要；② 各类候选数量（机票/火车票分去程返程、酒店，取自 `candidates`）；③ 工具组合方案总数（`combo_count`）；④ 四类代表方案分别对应哪套（🥇综合最优 / 💰价格最低 / ⏱️时间最短 / ❤️最符合偏好，取自 `tags`）；⑤ 审核剔除/修复情况（`summary` 的未通过/有隐患数量 + 修复轮次）。
- 表格与明细的评分列统一用 时间/价格/偏好/体验/政策/综合 六维数值。
- 候选池完整表格为**可选附录**，仅当用户要求核对候选时，于评估足迹之后附上：交通逐条列航班号/车次号、站点、时间、舱位/席别、价格；酒店逐条列名称、品牌、星级、房型、每晚价、评分、位置/商圈。
- **禁止向用户暴露内部名称**：最终 HTML 中**绝不允许**出现工具函数名、子智能体名、内部字段名与文件路径（如 `plan_itinerary`、`review_planner_result`、`query_destination_news`、`query_weather`、`query_travel_policy`、`retrieve_from_memory`、`record_to_memory`、`itinerary_review_agent`、`candidates`、`preference_basis`、`combo_count`、`total_transit_hhmm`、`total_budget`、`result_file` 等 `snake_case` 名称）；如需描述数据来源或处理环节，统一使用中文自然语（如"候选搜索""审核报告""目的地新闻查询""长期记忆召回""总时长""总预算""方案总数"）。若审核报告回传的 issues/suggestions 包含此类名称，透传前必须改写为中文描述。

## HTML 组件映射

生成的 HTML 包含以下区块（按出现顺序）：

1. **标题头**：出差事由、差旅单号、状态、出发倒计时提醒
2. **推荐方案 P1**：推荐理由、天气提醒、费用明细表、审核结论
3. **方案对比表**：P1/P2/P3/P4 的多列表格
4. **方案明细**：P1~P4 的详细列表（每个方案含去程/返程/酒店/总耗时/总价/评分/隐患或优势）
5. **Agent 行为说明**：6 个以内要点
6. **下一步操作**：3 个以内操作提示

### 组件样式映射

| 方案元素 | HTML 组件 | CSS 类/样式 |
|---|---|---|
| 标题头 | `.card` > `.header` + `.title-group` + `.meta` | 标题 22px、meta 14px 灰色 |
| 倒计时/提醒 | `.alert.alert-warning` | 黄色背景 `#fffbeb`、左侧图标 |
| 二级标题 `###` | `.section-title` | 18px、加粗、带 emoji 前缀 |
| 推荐原因段落 | `.recommend-reason` | 左侧蓝色边框 `#3b82f6`、浅灰背景 |
| 天气信息 | `.weather-box` > `.weather-item` | 两列响应式卡片 |
| 费用明细表 | `<table>` | 表头浅灰、合计行加粗、价格红色 |
| 审核结论 | `.audit-conclusion` | 绿色背景 `#f0fdf4` |
| 方案对比表 | `<table class="comparison-table">` | 小字号 13px、横向滚动 |
| 单个方案明细 | `.plan-item` | 按状态加 `.recommended` / `.warning` / `.failed` |
| 方案状态标签 | `.badge.badge-success` / `.badge-warning` / `.badge-danger` | 绿/黄/红 |
| 方案备注 | `.plan-note.success` / `.warn` / `.fail` | 对应状态色背景 |
| Agent 行为 | `.agent-actions` > `.action-item` | 响应式网格 2~3 列 |
| 下一步 | `.next-steps` | 蓝色背景 `#eff6ff`、带箭头列表 |

### 状态颜色语义

- **通过/推荐**：绿色系 `#f0fdf4` / `#15803d` / `#bbf7d0`
- **隐患/警告**：黄色系 `#fffbeb` / `#a16207` / `#fde68a`
- **未通过/错误**：红色系 `#fef2f2` / `#b91c1c` / `#fecaca`
- **中性信息**：灰色系 `#f8fafc` / `#475569` / `#e2e8f0`

## 工作流

### Step 1：组装方案数据（执行者：LLM）

从 `plan_itinerary` 返回结果和 `review_itinerary` 审核报告中提取以下数据：
- 用户请求（出发地、目的地、去程/返程日期、事由）
- 推荐方案（去程/返程交通详情、酒店详情、费用明细、六维评分）
- 全部方案对比数据（标签、交通、酒店、总耗时、总价、评分、审核状态）
- 审核结论（通过/隐患/未通过数量、修复情况）
- 天气摘要、候选数量、组合方案数、四类代表方案对应关系

### Step 2：生成 HTML 骨架（执行者：LLM）

使用以下单文件 HTML 模板，所有 CSS 内联在 `<style>` 中：

- `<!DOCTYPE html>` + `<html lang="zh-CN">`
- viewport meta 标签确保移动端可用
- 字体栈：`-apple-system, BlinkMacSystemFont, "Segoe UI", "PingFang SC", "Hiragino Sans GB", "Microsoft YaHei", sans-serif`
- 背景使用浅灰渐变：`linear-gradient(135deg, #f5f7fa 0%, #e4e8ec 100%)`

### Step 3：映射各区块到 HTML 组件（执行者：LLM）

按上方"组件样式映射"表格，将各内容区块映射到对应的 HTML 组件和 CSS 类。

### Step 4：应用状态颜色语义（执行者：LLM）

按上方"状态颜色语义"，为不同审核状态的方案应用对应颜色。

### Step 5：添加响应式适配（执行者：LLM）

在 `<style>` 中加入 `@media (max-width: 768px)`：

- `.card` 内边距缩小到 `20px 18px`
- 对比表支持横向滚动：`.comparison-table { display: block; overflow-x: auto; white-space: nowrap; }`
- `.header` 垂直排列
- `.agent-actions` 单列

### Step 6：调用 save_plan_html 工具（执行者：LLM）

将完整 HTML 字符串作为 `html` 参数传入 `save_plan_html` 工具：

```
save_plan_html(html="<完整 HTML 字符串>", title="上海 → 杭州 差旅行程方案")
```

工具会通过 SSE 将 HTML 推送至前端，前端在 iframe 中渲染完整方案页面。

调用成功后，你只需输出一句简短确认文案（如"方案已生成，请查看下方完整方案展示"），**不要重复输出方案正文**。

## 输出质量检查清单

- [ ] 所有价格数字使用红色加粗样式 `.price`
- [ ] 推荐方案 P1 使用绿色背景 `.recommended`
- [ ] 隐患方案使用黄色背景 `.warning`
- [ ] 未通过方案使用红色背景 `.failed`
- [ ] 表格保留表头且表体对齐
- [ ] 移动端有横向滚动或单列布局
- [ ] 方案数据全部取自 `plan_itinerary` 和 `review_itinerary` 的真实返回，不得编造
- [ ] 未编造用户偏好——偏好描述仅基于 `preference_basis` 命中项
- [ ] HTML 中无内部工具名/字段名等 `snake_case` 名称暴露
- [ ] 已调用 `save_plan_html` 工具提交 HTML

## 禁止事项

- 不要把 CSS 拆成独立 `.css` 文件；必须单文件 HTML。
- 不要删除方案中的任何方案或费用信息。
- 不要修改价格、航班号、酒店名等事实数据。
- 不要编造未提供的天气、政策、审核结论内容。
- 不要在 HTML 中暴露内部工具名、字段名（如 `plan_itinerary`、`combo_count`、`total_budget` 等 snake_case 名称）。
- 不要在调用 `save_plan_html` 后再输出方案 Markdown 正文——方案已通过 HTML 展示。
